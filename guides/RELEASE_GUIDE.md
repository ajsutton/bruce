# Release Guide

This is the source of truth for Bruce release execution. `justfile` defines each command; this
guide defines their order and approval boundaries.

## Conventions

- Every push to `main` automatically publishes an iOS TestFlight build and a GitHub prerelease
  containing the signed, notarised Mac zip, build number, and attested release manifest.
- RC: `v<MAJOR>.<MINOR>.<PATCH>-rc.<N>`; the workflow assigns the next RC number automatically
  using `MARKETING_VERSION` from the pushed commit and generates release notes from GitHub.
- Final: `v<MAJOR>.<MINOR>.<PATCH>`.
- Tags are immutable and are never deleted after they are pushed.
- A final tag points at the same commit as the latest tested RC for that version.
- iOS and macOS use the same marketing version and build number.
- iOS ships through TestFlight and the App Store.
- macOS ships as a directly distributed, Developer ID signed and notarised GitHub release zip.
- Final promotion reuses the tested TestFlight build and Mac zip; it does not rebuild them.

## One-time prerequisites

The manual setup instructions in `plans/RELEASE_AUTOMATION_PLAN.md` must be complete:

- Ruby 3.3 and the Bundler version locked in `Gemfile.lock` are available locally.
- Apple identifier `net.symphonious.bruce` exists with Associated Domains enabled.
- Widget identifier `net.symphonious.bruce.energy-widget` exists. Both iOS identifiers are
  associated with `group.net.symphonious.bruce`, include the shared Keychain access group, and
  have current App Store distribution profiles. After changing these capabilities, an explicitly
  approved operator runs `just refresh-ios-profiles` before the next release.
- Both macOS identifiers are associated with `group.net.symphonious.bruce`, include the shared
  Keychain access group, and have current Developer ID profiles. After changing these capabilities,
  an explicitly approved operator runs `bundle exec fastlane mac force_certificates` before the
  next release.
- The App Store Connect Bruce record exists.
- A team App Store Connect API key has been validated for upload, review submission, Match, and
  notarisation.
- A dedicated private Bruce Match repository contains App Store and Developer ID signing material
  for `net.symphonious.bruce` and `net.symphonious.bruce.energy-widget`. Bruce must not use
  Moolah's Match repository, encryption password, or repository credential.
- GitHub environments `rc-release` and `production-release` exist for release-secret scoping and
  do not require deployment approval. `rc-release` must allow deployments from `main` as well
  as RC tags.
- The environment secrets listed in the plan exist.
- GitHub Actions is allowed to create pull requests.

CI uses Match read-only. Creating or repairing signing material is a separate, explicitly approved
operator action.

## Release safety boundary

Automatic prereleases on `main` are authorized by the push and need no separate proposal.
For an optional manually created RC tag, show the user:

- version and tag;
- exact commit SHA;
- release notes;
- iOS signing and distribution path; and
- Mac signing and distribution path.

RC tags do not require explicit approval after the proposal is shown.

Before creating a final tag, show the user and obtain explicit approval for:

- version and tag;
- exact commit SHA;
- release notes;
- paired RC tag;
- TestFlight build number and attested Mac zip digest;
- iOS signing and distribution path;
- Mac signing and distribution path;
- App Store automatic release after approval; and
- proposed post-release marketing-version bump.

Creating the approved final tag is the final-release authorization. The GitHub environments scope
secrets but must not add a second deployment-approval gate.

## Automatic prereleases

`release-rc.yml` checks out the exact pushed SHA, creates a prerelease and RC tag with autogenerated
notes, then uploads TestFlight and the Mac assets. Its `GITHUB_TOKEN` creates the release in the
same run; the generated tag does not trigger another workflow. CI continues to run independently.
The release queue serializes runs and retains up to GitHub's limit of 100 pending runs; it does
not replace older pending pushes. TestFlight processing finishes before the next run allocates a
build number. The marketing version comes from the commit, so version bumps must land on `main`.

Use the run summary to find the generated tag, then `just release-wait <tag>` and
`just release-status <tag>` to inspect it. Smoke-test both platforms and verify the assets and
attestations as described below before promoting an automatic RC to final. A rerun on `main`
creates a fresh RC number; existing tags and assets remain immutable.

## Cut an RC manually (optional)

1. Run:

   ```sh
   just release-preflight
   ```

   It requires clean local `main`, exact synchronization with `origin/main`, authenticated `gh`,
   and successful CI for the pinned SHA. Do not fetch or pull between preflight and tag creation.

2. Inspect all intended changes since the prior release or RC. Confirm every intended change is
   present before continuing.

3. Run:

   ```sh
   just release-next-version rc
   ```

   Confirm `MARKETING_VERSION` in `project.yml` when the output requests it. A version change must
   land through a normal reviewed commit before restarting preflight.

4. Write concise tester-facing notes describing the change since `notes_base`. Save them under
   `.agent-tmp/release-notes-<version>.md`.

5. Show the release proposal. RC tagging does not require a separate approval pause.

6. Create the GitHub prerelease and tag:

   ```sh
   just release-create-rc <version> .agent-tmp/release-notes-<version>.md
   ```

7. Open the Actions run and verify its tag and commit.

8. Wait and inspect status:

   ```sh
   just release-wait v<version>
   just release-status v<version>
   ```

9. Confirm the prerelease contains:

   - `Bruce-<marketing-version>.zip`;
   - `build-number.txt`; and
   - `release-manifest.json`.

10. Verify the manifest and Mac zip attestations with `gh attestation verify`, scoped to
    `ajsutton/bruce` and `.github/workflows/release-rc.yml`.

11. Wait for App Store Connect processing, then smoke-test the TestFlight build on a physical iOS
    device. Install the latest published Mac release, including prereleases, with:

    ```sh
    just install-release-mac
    ```

    Launch `/Applications/Bruce.app` through Finder and smoke-test it. Do not smoke-test a local
    workflow output.

If an RC fails, fix the problem on `main` and cut the next RC number. Never move or delete the bad
tag and never replace its attested assets.

## Voice feature submission metadata

Before uploading a voice-enabled build, complete the App Store Connect encryption questionnaire
for the bundled WebRTC/BoringSSL and Sodium cryptography. The app deliberately omits
`ITSAppUsesNonExemptEncryption` while classification is pending, rather than asserting an
exemption. Record Apple's resulting declaration and any required compliance code in both app
plists before automating subsequent uploads.

Reviewers can choose **Try Demo** on the disconnected home screen without signing in. The demo
uses isolated, in-memory climate, charging, garage and energy clients. Controls change only sample
data; exiting discards the visit. Demo voice offers two sample agents, local spoken responses,
sample questions, a sample temperature command, mute and end-call controls. It never records the
microphone or connects to OpenClaw, and is explicitly labelled as simulated. Include these entry
and exit instructions in TestFlight and App Store review notes. Real authentication, remote audio,
CallKit, CarPlay and widgets still require a configured environment to exercise; the demo does
not claim to validate those integrations.

When providing live review access, supply OpenClaw/Cloudflare Access access as well as Home
Assistant access. Explain microphone permission and background audio during an active call, and
include the agent picker/call screen in review material. Explain that CallKit and the Voice over IP
background mode support user-initiated outgoing audio calls only; Bruce does not receive incoming
calls, use PushKit, or add calls to Phone Recents. Match App Store privacy answers to the
voice audio, retained conversation content, and account identifiers described in
`docs/privacy/index.html` and the app privacy manifest. Do not claim that all voice content is
transient: OpenClaw retains conversations under the gateway operator's retention settings.

## Local signing configuration

Keep local release credentials in the gitignored `.env.signing` file. Set it up once:

```sh
cp .env.signing.example .env.signing
chmod 600 .env.signing
bundle install
```

Fill in the file with the existing Bruce credentials: `DEVELOPMENT_TEAM`, `ASC_KEY_ID`,
`ASC_ISSUER_ID`, `ASC_KEY_FILEPATH`, and `MATCH_GIT_URL`.
Do not store the Match passphrase in this file. Match retrieves it from macOS Keychain, or
prompts securely and saves it to Keychain on first use.
`ASC_KEY_FILEPATH` points to the existing `.p8` private key, so it need not be copied or encoded.
For HTTPS Git authentication, also supply `MATCH_GIT_BASIC_AUTHORIZATION` if your Git credential
helper does not already provide access. An SSH Match URL can use your existing SSH identity.
The Git credential needs write access to the dedicated Bruce Match repository for profile refresh.

After enabling a capability in the Apple portal, run:

```sh
just refresh-ios-profiles
```

The target sources and exports `.env.signing`, checks all required values before invoking
Fastlane, and regenerates the iOS App Store profiles in Match. It does not build or publish a
release. It explicitly enables writable Match operation for this maintenance lane; ordinary CI
release lanes continue to use read-only Match. The Apple API key must permit provisioning-profile
creation. Do not broaden the CI key if it is intentionally read-only; use the existing local
bootstrap key described in `plans/RELEASE_AUTOMATION_PLAN.md`.

To use the same configuration with another local Fastlane lane, run this in the repository root:

```sh
set -a
source .env.signing
set +a
```

CI continues to use its existing GitHub environment secrets, including base64 `ASC_KEY_CONTENT`.
Never commit `.env.signing` or copy its contents into logs or chat.

## CarPlay voice submission

The developer account has Apple’s CarPlay Voice Based Conversation approval. Before signing
or uploading a CarPlay-enabled iOS build, enable the capability on both the
`net.symphonious.bruce` and `net.symphonious.bruce.debug` App IDs and regenerate profiles with
`com.apple.developer.carplay-voice-based-conversation`. An operator with release credentials runs
`just refresh-ios-profiles` after enabling the release App ID capability.
The widget App IDs do not need CarPlay. Do not substitute audio,
communication, or navigation entitlements. CarPlay voice requires iOS 26.4 or later; the phone
app remains available on iOS 26.

Include the voice-control screen and agent selection in review material. Explain that CarPlay
opens with agent selection, dials the selected OpenClaw agent immediately, returns to the list
after End, offers Mute during the conversation, and shows no AI
response text or Home Assistant panels. Sign-in and microphone permission are handled on the
phone. Smoke-test a cold CarPlay-only launch, phone/CarPlay handoff, mute/end from both surfaces,
backgrounding and disconnection using an approved profile before submission.

## Promote an RC to final

1. Confirm the latest RC for the current marketing version completed both platform smoke tests.

2. Complete all App Store metadata, privacy, pricing, screenshots, review contact details, and
   review access described in the implementation plan. A reachable Home Assistant review instance
   with active temporary credentials or a fully featured demo mode must remain available throughout
   App Review. Review notes must explain how to add and refresh the Energy Now widget and identify
   the Home Assistant energy and daily-statistics entities required to populate it.

3. Run:

   ```sh
   just release-preflight
   just release-next-version final
   ```

4. Write cumulative end-user notes since the previous final release and save them under
   `.agent-tmp/release-notes-<version>.md`.

5. Download the paired RC manifest and artifacts. Verify the attestations and show the user the
   final tag, RC tag, commit, build number, Mac digest, notes, automatic-release behaviour, and
   next proposed marketing version. Obtain explicit approval.

6. Create the final GitHub release and tag at the RC commit:

   ```sh
   just release-create-final <version> <rc-tag> .agent-tmp/release-notes-<version>.md
   ```

7. Open the Actions run and verify the displayed pairing and attested values.

8. Wait and inspect status:

   ```sh
   just release-wait v<version>
   just release-status v<version>
   ```

9. Confirm:

   - the existing TestFlight build was submitted for review with automatic release enabled;
   - the final GitHub release contains a byte-identical copy of the tested RC Mac zip; and
   - the workflow's one-line post-release version-bump PR was squash-merged.

10. Monitor App Store review. Workflow success means submission succeeded, not that Apple has
    approved or released the build.

## Recovery

- Processing delay: wait; do not rebuild.
- RC signing, upload, notarisation, or smoke-test failure: fix `main` and cut a new RC.
- Final metadata failure before submission: correct App Store Connect and rerun the failed job.
- Final rerun after submission: inspect App Store Connect first. The workflow must not create a
  second submission.
- Final Mac-copy failure: keep the tag, diagnose, and rerun the idempotent copy.
- Post-release bump failure: repair or manually merge the one-line PR; do not resubmit binaries.
- App Review rejection: fix `main`, choose a new marketing version, and run a fresh RC/final cycle.
- Compromised credential: revoke and rotate it at the source before rerunning anything.
